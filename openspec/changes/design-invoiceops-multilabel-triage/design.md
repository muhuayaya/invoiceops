## Context

项目根目录当前只有新初始化的 OpenSpec 规划结构，是一个绿地 PoC。业务动机见 [proposal.md](./proposal.md)，外部行为契约见 `specs/` 下五项能力规格。

约束已经确定：3 人协作、交付时间紧但具体周期未知；输入为中文、英文或中英混合文本；同一工单允许多个标签；数据采用公开资料和企业场景模拟数据；外部云端 LLM 只作为低置信度辅助；成果必须可本地运行并展示企业级边界，而不是声称已在真实企业生产验证。

参考项目 `D:\HWClass\NLP_Project\05_代码\TMFCode` 已具备随机森林、FastText、BERT、LLM、量化/蒸馏、Flask API 与 Streamlit 原型。新项目借鉴其“多模型对照、训练—预测—服务—界面”链路，但不复用参考项目的 Flask 服务层，后端 API 统一采用 FastAPI，并修正硬编码、重复模块、评估单一、缺少数据/模型版本、无鉴权审计和不可部署等生产缺口。

行业依据：Oracle 的发票校验覆盖税额、订购/收货/开票数量或金额差异、汇率及异常挂起，[Oracle 文档](https://docs.oracle.com/en/cloud/saas/financials/25d/fappp/how-invoices-are-validated.html)可支撑首版标签语义；企业路由拆为“分类”和“分派”两个阶段，[Microsoft Unified Routing](https://learn.microsoft.com/en-us/dynamics365/customer-service/administer/overview-unified-routing)可支撑分类结果与队列规则解耦。公开资料只能证明问题真实存在，不能替代目标企业的历史基线。

## Goals / Non-Goals

**Goals:**

- 在一台开发机或内部服务器上用 Docker Compose 一键启动 Web、API、worker、PostgreSQL、Redis 和模型跟踪组件。
- 支持中英双语多标签分类、逐标签阈值、拒识、高风险覆盖与受控 LLM 辅助。
- 形成可演示的业务闭环：工单接入 → 自动建议 → 队列推荐 → 人工复核 → 反馈留痕 → 训练候选。
- 让数据、标签、阈值、模型和预测结果全部可版本化、可追踪、可回滚。
- 以稳定接口和目录所有权支持 3 人并行开发，并通过自动化测试完成集成。
- 给出明确的 PoC 验收门槛，同时区分模型离线指标、系统指标和未来真实业务指标。

**Non-Goals:**

- PoC 不实现生产 ERP、采购或支付系统写回，也不自动批准付款、解除 hold 或修改银行账户。
- PoC 不做 PDF/OCR、附件病毒扫描、邮箱协议接入、企业 SSO、复杂组织架构和生产级多租户。
- PoC 不承诺 7×24 高可用、跨地域容灾或大规模在线训练。
- 外部 LLM 不作为最终裁决者，不直接生成训练真值，也不接收未脱敏原文。
- 模拟数据指标不等同于真实企业收益；错误转派下降、SLA 改善等只作为后续真实试点的验证指标。

## Decisions

### 1. 系统采用模块化单体加一个异步 worker

整体结构如下：

```text
┌─────────────────────── Browser ───────────────────────┐
│  工单提交  批次状态  人工复核  模型/审计只读看板     │
└──────────────────────────┬────────────────────────────┘
                           │ HTTPS / REST
                    ┌──────▼──────┐
                    │ FastAPI API │
                    │ auth/intake │
                    │ policy/audit│
                    └───┬─────┬───┘
                        │     │ enqueue
             ┌──────────▼┐   ┌▼──────────────┐
             │PostgreSQL │   │ Celery Worker │
             │业务+审计  │   │ 批量/LLM任务  │
             └───────────┘   └──┬───────┬────┘
                                │       │
                       ┌────────▼──┐  ┌─▼──────────────┐
                       │模型运行时 │  │LLM Adapter     │
                       │XLM-R/基线 │  │脱敏+预算+熔断  │
                       └─────┬─────┘  └────────────────┘
                             │ versioned artifact
                       ┌─────▼────────────┐
                       │ MLflow + Artifact│
                       │ 本地/S3适配器    │
                       └──────────────────┘
```

API、领域规则和持久化先部署为同一后端应用，批量分类和外部 LLM 请求由 worker 异步执行。与一开始拆微服务相比，这能减少部署、分布式追踪和接口协调成本；模块边界与事件 outbox 保留了未来拆分能力。

替代方案：纯 Streamlit 单体开发更快，但难以清晰隔离权限、API 契约和后台任务；完整微服务更贴近大型生产系统，但不适合 3 人短周期 PoC。

### 3. 标签体系与路由体系分离

标签回答“文本涉及什么问题”，路由规则回答“谁负责处理”。首版标签建议如下：

| 标签代码 | 中文名称 | 典型英文表达 | 风险 | 默认主队列 |
|---|---|---|---|---|
| `PRICE_VARIANCE` | 价格差异 | price mismatch | 中 | 采购运营 |
| `QUANTITY_RECEIPT_VARIANCE` | 数量/收货差异 | quantity/receipt mismatch | 中 | 收货与采购 |
| `TAX_CURRENCY_AMOUNT` | 税务/币种/金额异常 | tax, currency or amount issue | 中/高 | 财务税务 |
| `DUPLICATE_INVOICE` | 疑似重复发票 | duplicate invoice | 中 | 应付审核 |
| `MISSING_PO_OR_RECEIPT` | 缺少PO/收货凭证 | missing PO/receipt | 中 | 采购运营 |
| `PAYMENT_STATUS` | 付款/发票状态咨询 | payment status inquiry | 低 | 供应商服务台 |
| `SUPPLIER_MASTER_CHANGE` | 供应商主数据/收款信息变更 | vendor master/bank change | 高 | 主数据风控 |
| `OTHER_REVIEW` | 其他人工复核 | other/unclear | 中 | 人工分诊 |

一个工单可以同时命中多个标签。主队列由风险优先级、标签组合和版本化路由表确定，其他队列作为协同方；历史预测始终保留原标签版本和路由版本。

替代方案：直接把“部门”当类别实现简单，但组织变化会迫使模型重训，且无法表达同一问题需要多个团队协同。

### 4. 主要模型使用 XLM-R 多标签头，轻量模型作为可解释基线

主要模型采用 `xlm-roberta-base` 编码器加 sigmoid 多标签分类头，损失函数为带类别权重的 `BCEWithLogitsLoss`。XLM-R 原生覆盖中英文，避免维护两套模型；首轮优先全量微调，若硬件或周期不允许，再冻结部分层或使用参数高效微调。文本最大长度先设 256 tokens，由数据分布验证后调整。

轻量基线采用字符/词 n-gram TF-IDF + One-vs-Rest Logistic Regression；它在 Windows 环境更容易复现，也能提供成本、时延和可解释权重基线。参考项目的 FastText 可作为可选实验，不列为 MVP 阻塞项。

推理输出采用逐标签概率而不是 softmax；在验证集上为每个标签选择阈值，并单独设置“自动接受阈值”和“进入候选标签阈值”。阈值与模型分开版本化，使业务能在不重训时调整人工复核覆盖率。

替代方案：双语分别训练两套 BERT 会增加版本和路由复杂度；直接用 LLM 分类开发快，但成本、时延、稳定性和数据出域风险不适合作为主路径。

### 5. 数据采用“公开语料辅助 + 受控模拟 + 人工挑战集”三层策略

由于公开数据很难同时满足“供应商发票工单、中英双语、多标签”三个条件，PoC 不冒充拥有真实企业历史数据：

1. 公开的通用中英文客服/意图文本只用于验证清洗、语言处理和训练流水线。
2. 根据公开 ERP 异常定义编写场景矩阵，再用模板和受控 LLM 生成候选中英文工单；生成记录保存模板、提示词版本和来源。
3. 由团队人工审核、改写并补充多问题组合、否定句、缩写、拼写错误和代码混合文本，形成冻结挑战集。

同一模板、翻译对、近重复文本和同一模拟供应商上下文只能出现在一个数据切分中。采用多标签迭代分层切分，默认 train/dev/test 为 70/15/15；冻结测试集只用于最终验收。自动生成标签不直接视为真值，至少一名人工复核后方可进入训练集；挑战集应双人交叉复核。

数据卡至少记录：来源和许可、生成方式、脱敏状态、中英文比例、标签分布、多标签组合分布、重复率、文本长度、已知偏差和禁用用途。

### 6. LLM 只提供受控第二意见

主模型命中低置信度区间时，策略引擎先执行脱敏检查、标签白名单、调用预算和熔断检查。符合条件的文本才通过 `LLMProvider` 适配器发送；请求只包含脱敏正文、允许的标签定义和严格 JSON Schema。

LLM 返回的标签、置信说明和 provider/model/prompt 版本保存在独立的 `llm_suggestions` 记录中，不能覆盖主模型输出。无论 LLM 是否成功，该类工单的最终状态仍为 `needs_review`。超时建议为 8 秒，失败最多一次短重试；连续失败触发熔断并直接转人工。

这样既满足使用云端 LLM 辅助的需求，也能对成本、隐私和不稳定输出设置明确边界。具体提供商由环境变量选择，不把任何供应商 SDK 泄漏到领域层。

### 7. 数据库使用可审计的关系模型

PostgreSQL 是业务事实来源，核心表如下：

| 表 | 关键内容 | 约束 |
|---|---|---|
| `tickets` | 请求标识、来源、脱敏正文、语言、状态、保留期限 | `request_id` 唯一 |
| `batch_jobs` | 文件摘要、总数、成功/失败数、状态 | 不保存原始文件到日志 |
| `predictions` | 决策、模型/阈值/标签版本、耗时、trace | 每次推理追加记录 |
| `prediction_labels` | 标签代码、分数、是否来自主模型 | 关联预测版本 |
| `llm_suggestions` | 结构化建议、模型与提示词版本、成本/错误 | 不覆盖 prediction |
| `reviews` | 最终标签、路由、操作者、备注、修订号 | 只追加新修订 |
| `taxonomy_versions` | 标签快照、状态、校验值 | 发布后不可变 |
| `model_versions` | 数据/代码/制品/指标引用、状态 | 单一 active alias |
| `audit_events` | 主体、动作、对象、前后版本摘要、时间 | 应用层禁止 update/delete |
| `outbox_events` | 待发布内部事件及投递状态 | 与业务事务同时提交 |

原始模拟 CSV 和模型制品通过 `ArtifactStore` 接口保存；PoC 默认本地挂载目录，未来可切换 S3/MinIO 而不改变业务接口。

### 9. 安全与隐私采用 PoC 可兑现的最小控制

- API 使用 JWT；PoC 提供本地用户种子和 `admin`、`reviewer`、`observer` 三个角色，认证接口封装后可替换 OIDC。
- 脱敏器先用可测试规则遮盖邮箱、手机号、银行账号/IBAN、发票号及模拟供应商标识；规则无法保证识别所有真实 PII，因此真实企业数据接入前必须重新做数据映射与隐私评估。
- 日志不写正文；数据库中的脱敏正文、人工备注和审计查询均按角色授权。
- `.env`、API key 和令牌不进 Git；CI 执行秘密扫描，运行时通过环境秘密注入。
- 为原始文本、脱敏文本、建议和审计分别配置保留期；PoC 默认只保留模拟/公开数据，提供可审计清理命令。
- LLM 出域默认关闭，只有显式配置提供商、预算和脱敏策略后启用。

### 10. 可观测性、可靠性与降级

所有请求使用 `trace_id` 贯穿 API、worker、模型和审计。结构化日志至少包含时间、级别、组件、trace、版本、耗时和结果码。Prometheus 指标包括请求量、错误率、P50/P95 时延、各决策占比、标签分布、人工复核积压、LLM 调用量/失败/成本和模型加载状态。

`/healthz` 只反映进程存活；`/readyz` 检查数据库和当前模型。Redis 或 LLM 不可用时，单条主模型分类仍可服务；批量任务暂停或重试，低置信度样本转人工。模型启动失败时 readiness 失败，不能返回虚假的成功结果。

PoC 容量假设为：单实例峰值 5 QPS、日均不超过 10,000 条、单条正文不超过 5,000 字符、批次不超过 10,000 行。它们是压测输入而非生产承诺；超出时 API 返回明确限制错误。

### 11. 模型准入与项目验收分层

在冻结测试集上比较轻量基线和 XLM-R，模型卡必须报告多标签 `micro-F1`、`macro-F1`、逐标签 precision/recall/F1、Hamming loss、按语言分组结果、人工复核覆盖率、时延和模型大小。

建议 PoC 准入门槛：

| 层级 | 指标 | 门槛 |
|---|---|---|
| 模型 | Macro-F1 | ≥ 0.80 |
| 模型 | Micro-F1 | ≥ 0.85 |
| 风险 | `SUPPLIER_MASTER_CHANGE` recall | ≥ 0.95 |
| 公平性检查 | 中英文 Macro-F1 差值 | ≤ 0.08 |
| 系统 | 不调用LLM的单条预测 P95 | ≤ 800 ms（约定硬件，500次） |
| 系统 | 核心 API 错误率 | < 1%（验收压测） |
| 流程 | 高风险/低置信度进入人工复核 | 100% |
| 工程 | 单元、契约、集成和核心 E2E | 全部通过，无高危秘密泄漏 |

模拟数据容易让分数虚高，因此模型门槛只说明管线和方法达到 PoC 标准。真实试点应另行采集基线，并验证自动建议采纳率、二次转派率、分流时长和 SLA 违约率。

### 12. 测试与 CI/CD

CI 按以下顺序执行：格式和 lint → 类型检查 → 秘密扫描 → 单元测试 → OpenAPI/JSON Schema 契约测试 → 数据质量与泄漏测试 → 带 PostgreSQL/Redis 的集成测试 → 构建前后端镜像 → 镜像漏洞扫描。耗时较长的模型训练不在每次提交运行；固定小模型和小样本用于推理回归，完整训练通过手动工作流执行。

必须覆盖的 E2E 路径：中英混合多标签成功分类、低置信度转人工、供应商主数据高置信仍转人工、未脱敏文本禁止 LLM、LLM 超时降级、人工改标留痕、重复幂等键、批次部分失败、模型回滚。

### 13. 三人协作边界

| 成员 | 主要所有权 | 可独立验收输出 |
|---|---|---|
| A：数据与 ML | `ml/`、`configs/taxonomy`、`src/.../ml_runtime` | 数据卡、基线/XLM-R、评估报告、模型卡、版本化制品 |
| B：后端与平台 | `apps/api`、`apps/worker`、领域/application/adapters、`infra/` | OpenAPI、DB迁移、队列、审计、Docker Compose、运行指标 |
| C：前端与质量 | `apps/web`、`tests/e2e`、演示数据与验收脚本 | 工单/批次/复核/审计界面、E2E报告、演示手册 |

共享文件由指定负责人维护：B 维护 OpenAPI 与 Compose，A 维护标签和模型 schema，C 维护端到端验收清单。采用短分支和小 PR；合并前至少一人评审，修改共享契约需另外两人确认。Codex 可用于脚手架、测试、代码审查和文档生成，但每个 PR 的负责人必须理解并验证生成内容。

## Risks / Trade-offs

- **模拟数据导致虚高指标和语言风格单一** → 保留独立人工挑战集、按模板组去重切分、公开披露数据卡，并把真实业务收益列为未验证。
- **首版标签可能重叠或边界不清** → 在训练前用 50–100 条双语样例做两人试标，记录冲突并修订标签说明；低一致性标签合并或延期。
- **多标签长尾造成关键类召回不足** → 使用类别权重、逐标签阈值和定向补样；关键类召回是硬门禁且始终人工复核。
- **云端 LLM 引入隐私、成本和不稳定性** → 默认关闭、只发脱敏最小文本、预算/超时/熔断、结构化校验、失败转人工。
- **三人同时修改共享契约导致集成阻塞** → M0 先冻结 OpenAPI、标签 schema 和事件格式；共享文件设单一负责人并用契约测试守护。
- **XLM-R 在 CPU 上时延偏高** → 先测真实基线，再按需量化或导出 ONNX；轻量模型可作为临时降级，但不在未评估时提前增加优化分支。
- **模块化单体未来扩展有限** → 保持应用端口、适配器和 outbox 边界；只有在真实容量或团队规模证明需要时拆服务。
- **审计表并非真正防篡改存储** → PoC 通过应用权限和只追加约束演示；生产化需追加数据库权限隔离、WORM/外部审计存储与合规评估。

## Migration Plan

本项目为绿地 PoC，不需要旧系统数据迁移，按可回滚阶段部署：

1. 初始化仓库规范、依赖锁定、标签 v1、OpenAPI 草案与 Compose 基础设施。
2. 部署仅含轻量基线的垂直切片，验证接入、持久化、复核和审计。
3. 注册 XLM-R 候选模型；通过离线门禁后将 active alias 指向新版本，保留基线和上一稳定版本。
4. 以默认关闭的功能开关接入 LLM；先验证脱敏、schema、预算、超时和熔断，再在演示环境启用。
5. 执行冻结验收集、API/E2E 和性能测试；生成数据卡、模型卡、测试报告和演示脚本。

回滚顺序：关闭 LLM 开关 → 将 active model alias 回滚至上一稳定模型 → 若应用回归则恢复上一镜像和兼容数据库迁移。数据库迁移在 PoC 阶段只允许向前兼容的新增字段/表；需要删除或改义时先新增替代字段，避免应用和数据版本锁死。
