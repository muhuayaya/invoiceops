## Context

当前后端已经具备单条分类、脱敏、幂等、审计和角色鉴权能力，但没有管理员专属的数据管理入口；前端也没有展示已录入工单的列表。该变更需要同时扩展 API、前端和契约文档，且必须兼容现有业务字段与内部编码。

## Goals / Non-Goals

**Goals:**

- 复用单条分类服务完成管理员手工录入，避免形成第二套分类逻辑。
- 新增管理员专属的工单摘要查询和筛选能力。
- 在服务端强制执行管理员权限，前端只作为用户体验层的入口控制。
- 只返回脱敏文本和必要摘要，保留现有幂等与审计语义。

**Non-Goals:**

- 不提供任意字段的在线批量编辑；提供带幂等键和确认交互的单条/批量删除，以及按 `request_id` 的 CSV 批量覆盖。
- 不引入新的数据库表；已有工单、预测、审计和幂等记录作为数据来源。
- 不改变现有分类 API、标签编码、数据库字段或登录方式。

## Decisions

- 新增管理员录入接口 `POST /api/v1/admin/tickets`，请求体沿用单条分类字段并要求 `Idempotency-Key`；这样能保证手工录入与外部接入使用相同的校验、脱敏和分类路径。
- 新增管理员列表接口 `GET /api/v1/admin/tickets`，支持 `request_id`、`risk`、`status` 和 `limit` 查询参数，响应只包含脱敏正文和分类摘要。
- 新增管理员删除接口 `DELETE /api/v1/admin/tickets/{ticket_id}`、批量删除接口 `POST /api/v1/admin/tickets/batch-delete`，以及批量覆盖接口 `POST /api/v1/admin/tickets/batch-overwrite`；三者都要求 `Idempotency-Key`。
- 批量覆盖请求以 `request_id` 定位已有工单。服务端先校验整批目标和输入，再逐条移除当前业务记录并调用现有 `classify` 链路生成新版本；删除/覆盖前后追加 `ticket.deleted` 或 `ticket.overwritten` 审计事件，旧审计与操作幂等记录不被删除。
- 两个接口都使用现有 JWT 角色判断并只接受 `admin`；前端仅在管理员会话中渲染数据管理菜单，但不把前端隐藏当作安全边界。
- 列表从现有仓储内存索引读取并按创建时间倒序排序；SQLite/PostgreSQL 适配器已经在启动时加载工单，因此不需要迁移。
- 数据管理页提供手工表单、提交反馈、筛选控件和列表刷新；标签、路由、风险和状态继续通过前端中文展示映射转换，API 内部编码保持稳定。
- 数据管理页通过勾选列表执行删除，通过 CSV 文件执行批量覆盖；删除按钮必须经过浏览器确认，覆盖 CSV 必须包含 `request_id,source,text,taxonomy_version` 表头。

## Risks / Trade-offs

- [Risk] 现有仓储列表在超大数据量下需要全量加载 → [Mitigation] 首版限制返回数量并复用已有仓储，后续数据规模增长时再增加数据库分页索引。
- [Risk] 删除或覆盖可能造成业务数据误操作 → [Mitigation] 服务端 admin 强制鉴权、幂等键、批量全量预校验，前端删除前确认，审计记录不可删除。
- [Risk] 仅保存脱敏正文无法恢复原始敏感内容 → [Mitigation] 这是既有数据最小化策略，数据管理页明确展示“仅显示脱敏正文”。

## Migration Plan

1. 先部署后端接口、权限测试和 OpenAPI 更新。
2. 再构建前端并验证管理员和非管理员页面行为。
3. 在 VM Compose 中只重建 API/Web，确认健康检查和手工录入烟测通过。
4. 回滚时恢复 API/Web 镜像；由于不新增表或破坏性迁移，不需要数据回滚。
