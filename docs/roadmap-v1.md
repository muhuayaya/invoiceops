# InvoiceOps 后续演进路线

## 当前基线

当前项目是一个可运行的企业级 AI 应用 PoC，已经具备：

- React + FastAPI + PostgreSQL + Redis + Celery + Docker Compose；
- 单条分类、CSV 批次、人工复核、审计、指标和管理员数据管理；
- 角色权限、幂等控制、数据脱敏、持久化和 worker 重启恢复；
- TF-IDF 基线和 XLM-R 离线训练/评估记录。

需要如实说明的边界：线上 active runtime 仍是确定性关键词规则分类器；XLM-R v3 在 240 条受控数据上通过离线门禁，但尚未进入 serving，也不能把离线结果描述成真实企业收益。

## 第一优先级：公开仓库和安全基线

1. 将演示账号替换为企业身份源或至少改为部署时注入；
2. 强制生产环境使用随机 JWT 密钥，并在启动时拒绝默认密钥；
3. 用 GitHub Actions secret、Vault 或云密钥服务管理部署秘密；
4. 增加依赖、容器和源码 secret 扫描；
5. 为 PostgreSQL、Redis、MLflow 增加网络隔离、认证、备份和恢复演练。

验收标准：默认配置只能用于 development；生产配置缺少密钥或身份源时启动失败；仓库和镜像扫描不包含秘密。

## 第二优先级：真实数据与评估闭环

1. 引入经过授权和脱敏的真实工单；
2. 保持按模板、翻译组和供应商上下文分组切分，避免数据泄漏；
3. 建立人工标注指南、双人复核和冲突仲裁流程；
4. 按中文、英文、混合文本及关键高风险标签分别报告 Precision、Recall、F1、校准和人工转派率；
5. 以时间切分和新供应商切分补充冻结测试集。

验收标准：评估集不再主要依赖模拟模板；每次训练都能追溯数据版本、标签版本、代码提交和模型制品哈希。

## 第三优先级：XLM-R 线上影子验证

推荐顺序：

```text
制品打包 → 独立 serving → 单元/契约/性能测试 → shadow 流量
→ 与当前规则模型对比 → 小比例灰度 → 可回滚切换
```

上线前需要完成：

- 打包 XLM-R 权重和 Tokenizer，固定 Transformers/PyTorch 版本；
- 明确 CPU 内存、冷启动、吞吐和 P95 预算；
- 让模型服务通过统一 `predict()` 契约；
- 保存输入脱敏结果、模型版本、阈值版本和 trace id；
- 设定自动回滚条件，例如高风险标签召回下降、P95 超标或错误率升高。

## 第四优先级：生产级身份、权限和数据治理

- 接入 OAuth2/OIDC、LDAP 或企业 SSO；
- 将管理员高风险操作增加审批或二次确认；
- 增加按租户/组织隔离数据的权限模型；
- 为导出、覆盖、删除和保留期清理增加不可抵赖审计；
- 设计数据备份、恢复、归档和删除证明。

## 第五优先级：可观测性和交付

- 接入 Prometheus/Grafana 或云监控；
- 增加结构化日志集中采集、告警和 trace 查询；
- 完成镜像签名、SBOM、漏洞扫描和依赖自动更新；
- 将 Compose smoke、数据库迁移和回滚演练纳入 CI/CD；
- 进一步拆分 API、worker 和模型 serving 的扩缩容边界。

## 业务层可以继续做什么

- 接入邮件、ERP、采购或供应商门户；
- 增加发票与采购单/收货单的三单匹配；
- 增加队列 SLA、优先级和自动分派；
- 以人工复核结果形成主动学习数据集；
- 增加相似工单检索、重复工单合并和知识库建议；
- 将模型预测、人工决策和最终业务结果关联起来，衡量节省时间、转派率和误报率。

## 不建议现在就做的事

- 在真实生产流量未验证前直接把 XLM-R 替换线上规则模型；
- 只根据 240 条模拟数据宣称模型达到生产精度；
- 继续扩展页面功能，却不补充真实数据、评估和回滚证据；
- 把默认账号、默认 JWT 密钥或数据库端口直接暴露到公网。
