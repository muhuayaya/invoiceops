## 1. 项目简介

InvoiceOps 是一个面向中英混合发票/付款工单的运营工作台，支持：

- 单条工单分类和多标签预测；
- CSV 批次处理、进度查看和失败原因查看；
- 人工复核、接受/纠正预测、补充备注和查看历史；
- 按 `request_id` 查询审计记录；
- 指标和运营工作台；
- 仅 `admin` 可用的数据管理，包括手工录入、筛选、删除和批量覆盖。

推荐的完整本地结构如下：

```text
浏览器 :3000  ->  Web 页面  ->  API :8000
                                  |-- PostgreSQL（业务数据）
                                  |-- Redis（队列/缓存） -> worker
                                  `-- MLflow（实验跟踪）
```

## 3. 运行环境要求

### 3.1 你的实际部署边界

本项目实际采用“虚拟机内完整 Compose”方案：

| 设备 | 作用 | 是否需要 Docker CLI |
| --- | --- | --- |
| Windows 主机 | 使用 SSH 管理虚拟机、用浏览器访问页面 | 不需要；Docker 命令都在虚拟机中执行 |
| Docker 虚拟机 `VM_IP` | 运行 PostgreSQL、Redis、MLflow、API、worker、Web | 需要 Docker Engine 和 Docker Compose v2 |
| phpstudy_pro Redis | Windows 主机上的独立 Redis | 当前完整 Compose 不使用 |

项目在虚拟机中的目录为 `/home/VM_USER/invoiceops`。完整 Compose 会自动启动 PostgreSQL 和 Redis，并通过一次性 `migrate` 服务执行 Alembic 迁移，因此不需要在 Windows 上另外配置 PostgreSQL，也不需要让容器连接 phpstudy_pro 的 Redis。

### 3.2 Windows 主机需要

- Windows 10/11；
- PowerShell；
- Windows OpenSSH Client（用于执行 `ssh`）；
- 浏览器（Chrome、Edge 等）。

检查 SSH：

```powershell
ssh -V
Test-NetConnection VM_IP -Port 22
```

只有在选择“本机直接启动 API/Web”调试模式时，Windows 才需要：

- Python 3.11 或更高版本；
- Node.js 20 或更高版本；
- npm。

### 3.3 虚拟机需要

在虚拟机中检查：

```bash
docker --version
docker compose version
```

如果虚拟机中没有 Docker Engine 或 Compose v2，需要先在虚拟机安装并启动 Docker 服务。Windows 主机不需要再安装 Docker Desktop，除非你想把 Compose 改为在 Windows 本机运行。

## 4. 实际部署方式：虚拟机内完整 Docker Compose

### 4.1 从 Windows 通过 SSH 进入虚拟机

在 Windows PowerShell 执行：

```powershell
ssh -i "<SSH_PRIVATE_KEY_PATH>" VM_USER@VM_IP
```

如果首次连接提示确认指纹，确认虚拟机确实是 `VM_IP` 后输入 `yes`。登录成功后，下面命令都在虚拟机终端执行。

### 4.2 首次配置虚拟机 `.env`

进入项目目录：

```bash
cd /home/VM_USER/invoiceops
test -f .env || cp .env.example .env
```

确认 `.env` 中前端和跨域地址使用虚拟机 IP：

```bash
sed -i 's#^VITE_API_BASE_URL=.*#VITE_API_BASE_URL=http://VM_IP:8000#' .env
sed -i 's#^INVOICEOPS_CORS_ORIGINS=.*#INVOICEOPS_CORS_ORIGINS=http://VM_IP:3000#' .env
grep -E '^(VITE_API_BASE_URL|INVOICEOPS_CORS_ORIGINS|DATABASE_URL|REDIS_URL)=' .env
```

Compose 内部依赖必须保持服务名：

```ini
DATABASE_URL=postgresql+psycopg://invoiceops:invoiceops@db:5432/invoiceops
REDIS_URL=redis://redis:6379/0
```

不要把上面两个内部地址改成 `localhost`，也不要把 `REDIS_URL` 改成 phpstudy_pro 的 Redis 地址。`db` 和 `redis` 是 Compose 网络内的服务名。

### 4.3 首次构建并启动全部服务

在虚拟机项目目录执行：

```bash
docker compose config
docker compose up --build -d
```

首次构建会下载基础镜像和依赖，耗时可能较长。该命令会启动 6 个长期运行服务，并先执行一次数据库迁移：

- `db`：PostgreSQL 16，业务事实存储；
- `redis`：Redis 7，Celery broker/result backend；
- `mlflow`：实验跟踪服务；
- `migrate`：执行 `alembic upgrade head` 后退出；
- `api`：FastAPI 后端，映射虚拟机 `8000` 端口；
- `worker`：Celery 批次任务消费者；
- `web`：Vite 构建后的 Nginx 页面，映射虚拟机 `3000` 端口。

### 4.4 检查虚拟机服务

```bash
docker compose ps
curl --fail http://127.0.0.1:8000/healthz
curl --fail http://127.0.0.1:8000/readyz
curl --fail http://127.0.0.1:3000/
```

在 Windows 浏览器访问：

- Web 页面：<http://VM_IP:3000>
- API 文档：<http://VM_IP:8000/docs>
- 健康检查：<http://VM_IP:8000/healthz>
- 就绪检查：<http://VM_IP:8000/readyz>
- Prometheus 指标：<http://VM_IP:8000/metrics>

### 4.5 日常启动、更新和查看日志

Windows 再次使用时，先 SSH 登录：

```powershell
ssh -i "<SSH_PRIVATE_KEY_PATH>" VM_USER@VM_IP
```

然后在虚拟机执行：

```bash
cd /home/VM_USER/invoiceops
docker compose up -d
docker compose ps
```

修改 API、worker 或前端代码后重新构建相关服务：

```bash
docker compose up --build -d api worker web
```

修改 Compose 配置、Python 依赖或基础镜像后，重新构建全部服务：

```bash
docker compose up --build -d
```

查看日志：

```bash
docker compose logs -f api
docker compose logs -f worker
docker compose logs -f web
```

按 `Ctrl+C` 只退出日志查看，不会停止服务。

### 4.6 虚拟机停止、重启和数据重置

```bash
# 暂停服务，保留容器和数据
docker compose stop

# 恢复已暂停的服务
docker compose start

# 停止并移除容器，默认保留数据卷
docker compose down
```

不要随意执行：

```bash
docker compose down -v
```

`-v` 会删除 PostgreSQL、Redis、MLflow 等 Compose 数据卷，可能清空当前演示数据。只有明确要重置环境时才使用。

## 5. 配置文件说明

`.env.example` 是安全的本地默认配置；虚拟机首次部署时复制为 `/home/VM_USER/invoiceops/.env`。实际 VM 部署建议保留以下配置：

```ini
DATABASE_URL=postgresql+psycopg://invoiceops:invoiceops@db:5432/invoiceops
REDIS_URL=redis://redis:6379/0
MLFLOW_TRACKING_URI=http://mlflow:5000
INVOICEOPS_CELERY_ENABLED=true
INVOICEOPS_DATA_DB=/data/invoiceops.sqlite3
INVOICEOPS_BATCH_DB=/data/invoiceops-batches.sqlite3
```

`DATABASE_URL`、`REDIS_URL` 和 `MLFLOW_TRACKING_URI` 使用 Compose 服务名，只在容器网络内部解析，不能改成 `localhost`。PostgreSQL 和 Redis 都由 Compose 启动；Windows 上的 phpstudy_pro Redis 不参与本次部署。

从 Windows 浏览器访问虚拟机中的 Web/API 时使用：

```ini
VITE_API_BASE_URL=http://VM_IP:8000
INVOICEOPS_CORS_ORIGINS=http://VM_IP:3000
```

`VITE_API_BASE_URL` 在构建 Web 镜像时写入前端静态文件，因此修改后必须在虚拟机重新构建 `web`：

```bash
cd /home/VM_USER/invoiceops
docker compose up --build -d api web
```

虚拟机防火墙和 VMware 网络还需要允许 Windows 主机访问 TCP `3000` 和 `8000`。另一台不在 VMnet8 网络中的物理机不能直接访问 `VM_IP`，需要将虚拟机网卡改为 Bridged，或配置 NAT 端口转发；详见 [交付与运行手册](delivery/runbook-v1.md) 的“跨机器访问”。

## 7. 网页端功能使用

### 7.1 单条工单分类

1. 使用 `admin`、`reviewer` 或 `observer` 登录；
2. 进入单条分类页面；
3. 输入工单来源、工单文本和 taxonomy 版本；
4. 提交后查看预测标签、置信度、风险等级及是否需要人工复核；
5. 对低置信度或高风险结果进入复核页面处理。

LLM 默认关闭。当前运行时使用确定性 fallback 分类器，适合本地演示和流程验证，不应描述为已经部署了训练好的 XLM-R 模型。

### 7.2 CSV 批次处理

上传的 CSV 必须是 UTF-8 编码，并至少包含以下四列：

```csv
request_id,source,text,taxonomy_version
demo-001,email,"The invoice amount is wrong.",invoiceops-v1
demo-002,portal,"付款仍未完成，请协助查询。",invoiceops-v1
```

字段含义：

- `request_id`：工单唯一编号；
- `source`：来源，例如 `email`、`portal`、`internal`；
- `text`：工单正文；
- `taxonomy_version`：分类体系版本，当前默认 `invoiceops-v1`。

操作步骤：

1. 进入“批次处理”；
2. 选择 UTF-8 CSV 文件；
3. 上传后等待页面自动刷新处理状态；
4. 查看总进度、失败行数及失败原因；
5. 对失败行按照提示修正 CSV 后重新上传。

如果页面显示 `CSV must contain request_id, source, text, taxonomy version`，表示表头缺少必填字段或字段名称不正确。`channel` 可以作为可选列，但不能替代上述四列。

### 7.3 人工复核

人工复核用于处理高风险、低置信度或模型无法可靠判断的工单：

1. 进入“复核工作台”；
2. 按风险、队列、状态或 SLA 筛选；
3. 打开工单查看原文、预测标签和依据；
4. 选择接受预测、纠正标签或补充备注；
5. 提交后查看复核历史和处理结果。

常见业务标签会在页面显示中文名称，例如财务税务、应付账款复核、采购运营、收货采购、供应商服务台、主数据风险和人工分流。API/数据库仍保留稳定的内部编码，便于系统集成。

### 7.4 审计查询

进入“审计”页面，输入 `request_id` 查询该工单的分类、复核、覆盖、删除等操作记录。审计记录用于追溯“谁在什么时间做了什么操作”，业务数据删除不会自动删除历史审计证据。

### 7.5 指标和运营工作台

“指标”页面用于查看分类量、风险分布、复核情况、失败情况等运营数据；“运营工作台”用于按角色进入日常处理流程。

## 8. 管理员数据管理

只有 `admin` 账号可以使用“数据管理”模块。该模块用于维护录入的工单数据。

### 8.1 手工录入

1. 使用 `admin/admin` 登录；
2. 进入“数据管理”；
3. 填写 `request_id`、来源、正文和 taxonomy 版本；
4. 提交后刷新列表，确认数据已写入。

### 8.2 筛选和删除

- 可按工单编号、来源或关键词筛选；
- 可删除单条工单；
- 勾选多条后执行批量删除；
- 删除操作需要确认，后端会校验管理员身份并记录审计事件。

删除会移除当前业务记录及其关联的分类/复核数据，但不会删除审计历史。生产环境执行前应确认数据保留策略。

### 8.3 批量覆盖

批量覆盖用于按 `request_id` 更新已有工单，CSV 表头为：

```csv
request_id,source,text,taxonomy_version
demo-001,email,"The corrected invoice text.",invoiceops-v1
demo-002,portal,"修正后的付款工单内容。",invoiceops-v1
```

使用步骤：

1. 准备 UTF-8 CSV；
2. 确认每个 `request_id` 都是系统中已存在的工单；
3. 在“数据管理”中选择批量覆盖文件；
4. 确认预览内容无误后提交；
5. 刷新列表并通过审计页面核对覆盖记录。

覆盖操作会先进行整批校验；发现错误时整批不提交，避免只更新一部分数据。覆盖后的工单应重新执行分类或人工复核流程。

## 9. 本机开发方式：API 与 Web 分开启动

此方式适合修改代码、调试接口。它不依赖本机安装 PostgreSQL 和 Redis，API 会使用 SQLite；但完整的队列、worker 和 MLflow 行为应使用 Compose 验证。

### 9.1 安装依赖

在项目根目录执行：

```powershell
Set-Location D:\NLP_Enterprise_Level_Project
python -m pip install -r requirements.lock
npm ci
```

### 9.2 启动 API

打开第一个 PowerShell 窗口：

```powershell
Set-Location D:\NLP_Enterprise_Level_Project
New-Item -ItemType Directory -Force .data | Out-Null

$env:DATABASE_URL = ""
$env:REDIS_URL = ""
$env:INVOICEOPS_CELERY_ENABLED = "false"
$env:INVOICEOPS_DATA_DB = "$PWD\.data\invoiceops.sqlite3"
$env:INVOICEOPS_BATCH_DB = "$PWD\.data\invoiceops-batches.sqlite3"
$env:INVOICEOPS_CORS_ORIGINS = "http://localhost:3000,http://127.0.0.1:3000"

uvicorn apps.api.main:app --reload --host 0.0.0.0 --port 8000
```

保持该窗口运行。API 地址为 <http://localhost:8000>。

### 9.3 启动 Web

打开第二个 PowerShell 窗口：

```powershell
Set-Location D:\NLP_Enterprise_Level_Project
$env:VITE_API_BASE_URL = "http://localhost:8000"
npm run dev
```

浏览器访问 <http://localhost:3000>。

如果只想看前端本地演示，不启动 API，可在新的 PowerShell 窗口执行：

```powershell
Set-Location D:\NLP_Enterprise_Level_Project
Remove-Item Env:VITE_API_BASE_URL -ErrorAction SilentlyContinue
npm run dev
```

此时登录和数据来自前端演示模式，不代表后端接口可用。

## 10. 停止、重启和重建

### 虚拟机 Compose 模式

以下命令必须在 SSH 登录后的虚拟机终端执行：

```bash
cd /home/VM_USER/invoiceops

# 暂停服务，保留容器和数据
docker compose stop

# 恢复已暂停的服务
docker compose start

# 停止并移除容器，默认保留数据卷
docker compose down

# 修改代码或依赖后重新构建并启动
docker compose up --build -d
```

不要随意执行下面的命令，它会删除虚拟机上的 Compose 数据卷：

```bash
cd /home/VM_USER/invoiceops
docker compose down -v
```

`-v` 会删除 PostgreSQL、Redis、MLflow 等 Compose 数据卷，可能清空当前演示数据。只有明确要重置虚拟机环境时才使用。

### 分开启动模式

在运行 `uvicorn` 或 `npm run dev` 的窗口按 `Ctrl+C` 即可停止对应进程。SQLite 文件位于项目的 `.data` 目录中。

## 11. 常见问题排查

| 现象 | 处理方式 |
| --- | --- |
| Windows 执行 `ssh` 失败 | 确认虚拟机已开机、IP 为 `VM_IP`，并检查 `Test-NetConnection VM_IP -Port 22`。 |
| SSH 后 `docker` 或 `docker compose` 未找到 | 在虚拟机安装并启动 Docker Engine 和 Compose v2；Windows 主机不需要安装 Docker CLI。 |
| Web 页面打不开 | 在虚拟机执行 `docker compose ps`，确认 `web` 为运行状态；查看 `docker compose logs web`；Windows 侧检查 TCP `3000`。 |
| 页面提示 `Failed to fetch` | 检查 `http://VM_IP:8000/healthz`；检查 `.env` 中 `VITE_API_BASE_URL` 和 `INVOICEOPS_CORS_ORIGINS`；改动后重新构建 Web。 |
| API `readyz` 返回 503 | 在虚拟机查看 `docker compose logs api db redis mlflow`，等待依赖健康后重启 API。 |
| 登录成功但页面没有真实数据 | 检查 Web 构建时是否设置了 `VITE_API_BASE_URL`；未设置时会进入前端演示模式。 |
| 直接启动 API 时连接 `db` 失败 | 清空 `DATABASE_URL`，因为 `db` 是 Compose 内部服务名；分开启动时使用 SQLite。 |
| CSV 上传失败 | 确认文件为 UTF-8，且包含 `request_id,source,text,taxonomy_version` 四列。 |
| “数据管理”菜单不可见 | 退出后使用 `admin/admin` 登录；`reviewer` 和 `observer` 没有数据管理权限。 |
| 另一台物理机无法访问页面 | `VM_IP` 只适用于宿主机或已接入 VMnet8 的设备；改用 Bridged 网络或配置 NAT 端口转发。 |
| 端口 3000 或 8000 被占用 | 在虚拟机查看占用端口，或修改 Compose 端口映射及 `VITE_API_BASE_URL` 后重新构建 Web。 |

查看端口占用示例：

```powershell
Get-NetTCPConnection -LocalPort 3000,8000 -ErrorAction SilentlyContinue
```

## 12. 推荐的启动后自检

完整 Compose 部署的自检命令在虚拟机执行：

```bash
cd /home/VM_USER/invoiceops
docker compose ps
curl --fail http://127.0.0.1:8000/healthz
curl --fail http://127.0.0.1:8000/readyz
curl --fail http://127.0.0.1:3000/
```

Windows 主机或其他访问端可检查网络连通性：

```powershell
Test-NetConnection VM_IP -Port 3000
Test-NetConnection VM_IP -Port 8000
```

如果在 Windows 项目目录安装了开发依赖，再执行代码级检查：

```powershell
Set-Location D:\NLP_Enterprise_Level_Project
python scripts/run_demo.py
pytest -q
npm run check
npm run build
```

其中 `scripts/run_demo.py` 会执行项目内置演示流程并生成演示证据；它不替代浏览器端的人工验收。

## 13. 当前项目边界

- 默认 LLM 关闭；超时、预算耗尽或熔断时进入人工复核；
- 无 Celery/Redis 的本地开发模式会使用 FastAPI 后台任务 fallback，生产环境应使用完整队列方案；
- 当前 API/Compose 镜像未打包本地训练模型制品，active runtime 仍是确定性 fallback；
- 默认账号、默认 JWT 密钥和本地配置只适合开发/演示，不适合直接暴露到公网；
- 不要将 PostgreSQL、Redis、MLflow 的内部端口直接暴露到公网。
