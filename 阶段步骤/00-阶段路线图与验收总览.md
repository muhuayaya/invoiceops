# InvoiceOps 中英双语多标签分流 PoC：阶段路线图与验收总览

## 1. 项目目标与规格摘要

本项目是一个可本地运行的企业级 PoC，服务于中英文或中英混合的供应商发票异常与付款咨询工单。目标是形成一条可演示、可追溯的业务闭环：

> 工单接入 → 多标签分类与队列建议 → 人工复核 → 反馈留痕 → 训练候选数据。

规格明确采用“模块化单体 + 异步 worker”，并使用 FastAPI、React + TypeScript、PostgreSQL、Redis、MLflow、PyTorch/Transformers 和 Docker Compose。主模型为 XLM-R 多标签模型；TF-IDF + One-vs-Rest Logistic Regression 是成本、时延与可解释性对照基线。外部云端 LLM 仅在脱敏和策略检查均通过的低置信度场景中提供第二意见，且结果仍须人工复核。

首版标签固定为八类：`PRICE_VARIANCE`、`QUANTITY_RECEIPT_VARIANCE`、`TAX_CURRENCY_AMOUNT`、`DUPLICATE_INVOICE`、`MISSING_PO_OR_RECEIPT`、`PAYMENT_STATUS`、`SUPPLIER_MASTER_CHANGE` 和 `OTHER_REVIEW`。标签回答“涉及什么问题”；版本化路由规则回答“由谁处理”。同一工单可命中多个标签。

## 2. 范围边界

### 本 PoC 包含

- 单条 REST API 接入、CSV 批量导入、输入校验、脱敏状态与幂等处理。
- 中英双语多标签预测、逐标签阈值、置信度校准、拒识、高风险覆盖及受控 LLM 辅助。
- 人工复核队列、接受/改标/备注、训练候选沉淀和可追溯审计。
- 标签、路由、阈值、数据集、模型、制品与预测结果的版本管理、准入和回滚。
- 最小 RBAC、结构化日志、指标、健康检查、降级、CI 门禁，以及 Docker Compose 一键运行。

### 明确不包含

- ERP、采购或支付系统写回；自动付款、自动解除发票挂起、自动修改供应商银行账户。
- PDF/OCR、附件病毒扫描、邮箱协议接入、企业 SSO、复杂组织架构或生产级多租户。
- 7×24 高可用、跨地域容灾、大规模在线训练，或将模拟数据效果表述为真实业务收益。
- 将 LLM 作为最终裁决者、让其生成训练真值，或向其发送未经脱敏的原文。

## 3. 实施总路线与依赖关系

```text
阶段 1：M0 仓库与共享契约
  └─→ 阶段 2：数据与评估基线 ─→ 阶段 3：主要模型与模型生命周期
  └─→ 阶段 4：后端领域与持久化 ─→ 阶段 5：批量任务与 LLM 辅助
       └───────────────────────→ 阶段 6：运营工作台
阶段 3 + 4 + 5 + 6 ───────────→ 阶段 7：安全、可观测性与部署
阶段 7 + 各阶段测试证据 ───────→ 阶段 8：端到端验收与交付
```

阶段 1 是所有并行开发的共同前置。阶段 2 与阶段 4 可在契约冻结后并行推进；阶段 3 依赖阶段 2 的冻结数据切分；阶段 5 建立在后端持久化和模型推理契约上；阶段 6 依赖已冻结的 API 契约并与阶段 5 联调；阶段 8 只在核心链路、工程门禁和部署证据齐全后进入。

## 4. 八个实施阶段

### 阶段 1：M0 仓库与共享契约

**对应任务**：第 1 章（1.1–1.5）
**阶段目标**：建立三人可并行协作的项目骨架，并冻结标签、API、事件和验收口径。
**前置输入**：已确认的 proposal、design、五项能力规格及本任务清单。
**主要工作与交付物**：

- 创建 Python、React、ML、测试、配置和基础设施目录；补齐 `.gitignore`。
- 锁定 Python 与前端依赖，提供统一开发命令。
- 发布 `invoiceops-v1` 标签、风险、样例、路由和阈值 JSON Schema。
- 冻结 OpenAPI v1 草案、标准错误响应、幂等头和 CSV 模板。
- 形成 ADR，记录标签 v1、API v1、事件格式、PoC 指标及明确的文件所有权。

**退出验收**：

- 新环境可完成依赖安装；敏感制品、模型制品和本地数据卷不被 Git 跟踪。
- Schema 能解析，未知标签和非法阈值被校验拒绝；API 示例请求有效。
- 三名成员均确认共享契约，且 A/B/C 所有权无空缺。

**依赖/门禁**：未冻结前，不允许破坏性改动标签、OpenAPI 或事件格式；共享契约变更须三人评审。

### 阶段 2：数据与评估基线

**对应任务**：第 2 章（2.1–2.6）
**阶段目标**：构建可信、可复现且不冒充真实企业数据的中英双语多标签数据与基线评估链路。
**前置输入**：阶段 1 的标签 v1、Schema 和评估口径。
**主要工作与交付物**：

- 公开资料与模拟数据来源清单、许可/用途/禁用范围和输入校验值。
- 覆盖八类标签、多标签组合、否定句和中英混合文本的场景矩阵与模板。
- 数据规范化、语言识别、规则脱敏、白名单元数据处理。
- 近重复/模板组检测和 70/15/15 多标签迭代分层切分。
- 经人工审核的训练候选、双人复核冻结挑战集及数据卡。
- TF-IDF + One-vs-Rest Logistic Regression 基线、统一评估报告。

**退出验收**：

- 每个输入可追溯来源和校验值；各目标标签及组合均有覆盖样本。
- 邮箱、手机号、IBAN/银行账号、发票号和混合语言脱敏测试通过。
- 模板、翻译对、近重复文本和模拟供应商上下文不跨训练/验证/测试集泄漏。
- 数据卡记录标签/语言/组合分布、重复率、文本长度、已知偏差；评估含 micro/macro-F1、逐标签指标、Hamming loss、语言分组、时延和模型大小。

**依赖/门禁**：冻结测试集仅用于最终验收；未人工复核的自动生成标签不得直接作为训练真值。

### 阶段 3：主要模型与模型生命周期

**对应任务**：第 3 章（3.1–3.6）
**阶段目标**：交付可替换的 XLM-R 主模型、可解释基线和受控的模型准入/回滚机制。
**前置输入**：阶段 2 的冻结数据版本、数据卡、基线与评估器。
**主要工作与交付物**：

- XLM-R 多标签加载器、sigmoid 分类头、固定随机种子训练配置。
- 首轮训练记录、误差分析、模型卡与冻结数据集关联的制品。
- 逐标签候选阈值、自动接受阈值、置信度校准和拒识原因码。
- 统一模型运行时与版本化制品装载接口。
- 模型注册、准入、`active alias`、上一稳定版本回滚。
- 在约定硬件上的冻结评估和至少 500 次性能测试报告。

**退出验收**：

- 小样本固定种子重复运行结果一致；基线与 XLM-R 均能通过同一推理契约加载。
- 模型卡报告模型/数据/代码/制品版本、误差样例与语言分组结果。
- 低置信度、无标签及冲突组合产生预期拒识原因；关键类别不达标时禁止提升。
- 回滚后新请求使用上一稳定模型；未达既定门槛时如实记录阻塞，不能伪造通过。

**依赖/门禁**：模型升级必须比较基线与 XLM-R，并检查 Macro-F1 ≥ 0.80、Micro-F1 ≥ 0.85、`SUPPLIER_MASTER_CHANGE` recall ≥ 0.95、中英文 Macro-F1 差值 ≤ 0.08；性能门槛以约定硬件上的无 LLM P95 ≤ 800 ms（500 次）验证。

### 阶段 4：后端领域与持久化

**对应任务**：第 4 章（4.1–4.7）
**阶段目标**：建立可审计的业务事实来源和单条工单到复核的核心 API 链路。
**前置输入**：阶段 1 的 OpenAPI/事件契约；阶段 3 的统一推理契约在模型接入时成为前置。
**主要工作与交付物**：

- 标签、工单、预测、复核、模型版本、审计领域对象和状态转换。
- PostgreSQL 核心 schema、可重复迁移、唯一键/外键与只追加审计约束。
- 单条分类接入、字段与长度校验、白名单元数据、`trace_id` 和幂等控制。
- 模型运行时、逐标签阈值、高风险覆盖和版本化路由规则接入。
- 人工复核查询/追加决策 API、训练候选规则、审计查询 API 与 outbox。

**退出验收**：

- 空库和已有库迁移均成功；非法状态转换、空文本、超长正文被拒绝。
- 同幂等键同体返回首次结果，同键异体返回冲突，且无重复业务记录。
- 中英混合多标签、低置信度和供应商主数据变更的集成测试通过。
- 接入、预测、路由、复核、模型提升/回滚可按 `request_id` 还原有序审计链；复核历史只追加、不覆盖。

**依赖/门禁**：高风险 `SUPPLIER_MASTER_CHANGE` 与低置信度结果必须进入人工复核，不因高置信度绕过。

### 阶段 5：批量任务与 LLM 辅助

**对应任务**：第 5 章（5.1–5.5）
**阶段目标**：实现可恢复的 CSV 异步批处理，并为低置信度样本提供不越权的 LLM 第二意见。
**前置输入**：阶段 4 的持久化、审计和单条分类链路；阶段 3 的模型推理和阈值策略。
**主要工作与交付物**：

- Redis、Celery worker、批次状态机与任务恢复机制。
- CSV 上传、逐行校验、异步分类、进度及逐行错误查询。
- `LLMProvider` 可替换接口、版本化提示词和严格 JSON Schema。
- LLM 脱敏门禁、默认关闭开关、预算、8 秒超时、一次短重试、熔断与人工降级。
- 独立的 `llm_suggestions` 持久化记录。

**退出验收**：

- worker 重启可恢复未完成任务，且不重复创建业务记录；混合有效性文件能处理有效行并返回带行号、原因的错误行。
- fake provider 契约测试拒绝未知标签和无效 JSON。
- 未脱敏、超预算、超时和连续失败均不调用或停止调用 LLM，全部转人工复核。
- LLM 建议包含 provider/model/prompt 版本，不覆盖主模型预测，也不自动成为最终决策。

**依赖/门禁**：LLM 出域默认关闭；只有显式配置提供商、预算和脱敏策略后才允许启用。

### 阶段 6：运营工作台

**对应任务**：第 6 章（6.1–6.5）
**阶段目标**：让运营人员完整完成提交、批次查看、人工复核和审计查询，并获得只读运行可视性。
**前置输入**：阶段 1 的冻结 OpenAPI；阶段 4/5 可用的 API 与鉴权行为。
**主要工作与交付物**：

- React + TypeScript 应用壳、路由、API client、登录态和受保护页面。
- 单条中英文本提交及多标签结果页。
- CSV 上传、批次进度、逐行错误展示。
- 人工复核队列、风险排序/筛选、接受/改标/追加备注与修订历史。
- 请求级审计时间线和只读运行看板（错误率、时延、复核积压、LLM 降级）。

**退出验收**：

- 本地前端构建成功，未登录不能访问受保护页面。
- 结果完整显示标签分数、语言、路由、决策状态及模型/阈值/标签版本。
- 混合有效性批次显示进度及错误详情；高风险工单优先显示，二次修订历史可查。
- 审计可按请求追踪事件，运行指标可只读查看。

**依赖/门禁**：前端不自行解释模型或重建路由规则，以版本化 API 输出为唯一事实来源。

### 阶段 7：安全、可观测性与部署

**对应任务**：第 7 章（7.1–7.6）
**阶段目标**：补齐 PoC 可兑现的最小安全控制、故障可见性、降级行为与可复现实例部署。
**前置输入**：阶段 4/5/6 的核心业务路径和运行组件。
**主要工作与交付物**：

- 本地 JWT 认证与 `admin`、`reviewer`、`observer` 权限矩阵。
- 结构化日志与贯穿 API/worker/模型的 `trace_id`。
- `/healthz`、`/readyz`、Prometheus 指标和既定降级行为。
- 分类型保留策略及可审计的数据清理命令。
- API、worker、web 镜像、Docker Compose、无秘密 `.env.example`。
- CI：lint、类型检查、秘密扫描、单元/契约/数据质量/集成测试、前端构建和镜像扫描。

**退出验收**：

- 各角色允许/拒绝路径验证通过，授权失败进入审计。
- 日志扫描不含正文、凭据或受保护字段；模型未加载时 `/healthz` 通过而 `/readyz` 失败。
- LLM 故障时主模型仍能服务；过期正文删除或匿名化后仍保留最小审计证明。
- 干净环境以 `.env.example` 一条命令启动完整依赖；故意引入 CI 失败能阻止合并。

**依赖/门禁**：不得把真实 `.env`、令牌或 API key 提交到仓库；Redis 或 LLM 失败不得伪造成功，必须按规格暂停/重试或转人工。

### 阶段 8：端到端验收与交付

**对应任务**：第 8 章（8.1–8.6）
**阶段目标**：以自动化、性能、风险和冷启动证据确认 PoC 的可演示性与边界真实性。
**前置输入**：阶段 1–7 的测试通过记录、运行环境、冻结数据/模型版本和交付文档草案。
**主要工作与交付物**：

- 核心 E2E 自动化：多标签成功、低置信转人工、高风险强制复核、脱敏禁用 LLM、LLM 超时降级、幂等冲突、批次部分失败、模型回滚。
- 单实例 5 QPS、正文 5,000 字符、批次 10,000 行的约束/压测报告。
- 威胁走查、数据泄漏走查、事前复盘及 P0 风险闭环。
- 数据卡、模型卡、指标局限、真实试点待验证项、README、演示账号和运行/降级/回滚/清理手册。
- 跨成员冷启动验证及按 M0–M4 的最终演示证据。

**退出验收**：

- 所有规定 E2E 场景通过；核心 API 验收压测错误率 < 1%，并报告吞吐、P50/P95 与资源使用。
- 高风险、隐私和泄漏风险无未关闭 P0；文档不把模拟数据效果写成真实业务收益。
- 另一名成员可按文档完成冷启动；最终演示能完整展示提交、预测、人工复核、审计、批量处理和指标。

**依赖/门禁**：未保存测试证据与验收结论不得宣告完成；真实业务收益（如 SLA 改善、二次转派下降）必须留待后续试点验证。

## 6. 关键风险、缓解措施与门禁

| 风险 | 规格内缓解措施 | 必经门禁 |
|---|---|---|
| 模拟数据虚高、语言风格单一 | 独立人工挑战集、模板组去重切分、数据卡披露偏差 | 冻结测试集隔离；报告明确不等于真实收益 |
| 标签边界重叠 | 训练前以 50–100 条双语样例双人试标，记录冲突并修订说明 | 标签 v1 评审后才进入规模化数据/训练 |
| 长尾标签关键召回不足 | 类别权重、逐标签阈值、定向补样、高风险强制复核 | `SUPPLIER_MASTER_CHANGE` recall ≥ 0.95；否则不可提升 |
| LLM 隐私、成本或不稳定 | 默认关闭、最小脱敏正文、预算、超时、一次重试、熔断 | 未脱敏/超预算/失败一律转人工；LLM 不得作最终裁决 |
| 三人并行修改共享契约 | M0 冻结 OpenAPI、标签 schema、事件格式；指定负责人 | 共享契约变更须三人评审与契约测试 |
| XLM-R CPU 时延超标 | 先测真实基线；按需量化或 ONNX；基线仅作评估后的临时降级 | 约定硬件 500 次测试、无 LLM P95 ≤ 800 ms |
| 审计不可真正防篡改 | 应用权限、只追加约束、完整审计链；生产化另行评估 WORM 等能力 | 接入至回滚事件均可按 `request_id` 还原 |
| 环境/部署不可复现 | 依赖锁定、Docker Compose、`.env.example`、冷启动演练 | 他人成员机器冷启动成功才可交付 |

## 7. 最终验收总门槛

以下门槛同时满足，才可将本变更标记为已完成的 PoC：

- 冻结测试集达到 Macro-F1 ≥ 0.80、Micro-F1 ≥ 0.85，关键高风险标签 recall ≥ 0.95，中英文 Macro-F1 差值 ≤ 0.08。
