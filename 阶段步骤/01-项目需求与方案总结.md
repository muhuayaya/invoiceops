# 项目需求与方案总结

> **状态：规划中的 PoC（概念验证）**。本文基于 `proposal.md`、`design.md` 和 `tasks.md` 汇总项目范围与方案；它描述的是拟建设能力和验收目标，**不代表系统已经实现、上线或在真实企业数据上验证**。

## 1. 为什么要做

企业财务共享中心会收到中文、英文和中英混合的供应商邮件或内部工单。一条文本可能同时包含价格差异、收货数量不符、税务或币种异常、付款状态查询、供应商资料变更等多个问题。

目前依赖人工阅读、标记和转派，容易出现重复流转、响应延迟，以及审计链路不完整。项目拟通过“多标签识别”和“规则化路由建议”减少人工分诊负担，同时保留高风险场景和不确定结果的人工把关。

## 2. 系统要做什么

本 PoC 拟交付一个可本地或内部服务器运行的供应商发票异常与付款咨询分流系统，形成以下闭环：

```text
工单接入 → 文本脱敏与校验 → 多标签分类 → 路由建议
        → 高风险/低置信人工复核 → 审计留痕 → 训练候选反馈
```

计划支持的能力包括：

- 接收单条工单 API，以及 CSV 批量导入。
- 对中英双语或混合文本进行多标签分类；同一工单可以命中多个问题类型。
- 根据标签组合、风险等级和版本化路由规则建议主处理队列及协同队列。
- 提供人工复核工作台，用于接受、改标、补充备注和查看修订历史。
- 记录模型、标签、阈值、路由、人工决策和预测事件版本，便于追溯与回滚。
- 通过健康检查、指标、结构化日志和 Docker Compose 支持演示、测试和运行观察。

首版候选标签为：价格差异、数量/收货差异、税务/币种/金额异常、疑似重复发票、缺少 PO/收货凭证、付款/发票状态、供应商主数据/收款信息变更，以及其他人工复核。

## 3. 明确不做什么

为保持 PoC 边界，本项目**不会**：

- 写回 ERP、采购或支付系统；不会自动批准付款、解除发票挂起，或修改供应商银行账户。
- 实现 PDF/OCR、附件病毒扫描、邮箱协议接入、企业 SSO、复杂组织结构、多租户、生产级高可用或异地容灾。
- 把外部云端 LLM 作为最终决策者，也不会将未脱敏原文发送给 LLM。
- 用公开或模拟数据的评估结果宣称真实业务收益；错误转派率、SLA 改善和采用率仍需真实试点验证。

## 4. 关键架构

系统采用“模块化单体 + 异步 worker”，以适应三人短周期协作：

```text
浏览器（React + TypeScript）
          │ HTTPS / REST
FastAPI API（认证、接入、策略、审计）
   ├── PostgreSQL（业务事实与审计记录）
   └── Celery Worker + Redis（批量任务与受控 LLM 任务）
                ├── 模型运行时（XLM-R / 轻量基线）
                └── LLM 适配器（脱敏、预算、超时、熔断）

MLflow + 本地或对象存储（模型、数据和实验制品）
```

- API、领域规则和持久化优先部署为一个后端应用，降低早期服务拆分与运维复杂度。
- 批量分类和外部 LLM 调用放入异步 worker，避免阻塞主请求。
- 使用 PostgreSQL 保存业务事实和只追加的审计信息；模型制品通过抽象存储接口管理。
- API、标签体系、路由规则与 JSON Schema 作为共享契约，先冻结再并行开发。

## 5. 模型与数据策略

### 模型策略

- **主模型**：`xlm-roberta-base` 加 sigmoid 多标签分类头，覆盖中文和英文；按标签输出独立概率而非互斥类别。
- **基线模型**：TF-IDF + One-vs-Rest Logistic Regression，用于成本、时延、可解释性和效果对照。
- **阈值策略**：每个标签分别设置候选、自动接受和拒识阈值，阈值独立版本化，业务可在不重训模型时调整人工复核覆盖率。
- **风险覆盖**：低置信度、无可接受标签及高风险的供应商主数据变更，即使预测分数高也必须进入人工复核。
- **LLM 辅助**：仅为合格的低置信样本提供受控“第二意见”。请求必须已脱敏，并受白名单、预算、8 秒超时、一次短重试和熔断控制；LLM 建议独立保存，绝不覆盖主模型结果或自动成为最终结论。

### 数据策略

项目不假定拥有真实企业历史数据，而采用三层数据：公开通用中英文文本用于验证流水线；依据公开 ERP 异常语义构造受控模拟场景；由人工审核和补充形成含多问题、否定句、缩写、拼写错误和代码混合文本的挑战集。

训练、验证和测试默认按 70/15/15 进行多标签迭代分层切分。同一模板、翻译对、近重复文本和同一模拟供应商上下文不得跨切分出现。自动生成标签不直接作为训练真值，至少需要一名人工复核；冻结挑战集需要双人交叉复核。

每个数据版本需配套数据卡，记录来源与许可、生成方式、脱敏状态、语言与标签分布、重复率、已知偏差及禁用范围。

## 6. 业务闭环与路由原则

标签回答“工单涉及什么问题”，路由回答“谁负责处理”，两者必须解耦。系统按风险优先级、标签组合和版本化路由表生成主队列及协同队列；历史结果始终保留当时的标签与路由版本。

人工复核人员可接受或修改建议。每次决定都以追加修订方式保留操作者、备注和最终标签；审核后的反馈仅作为后续训练候选，仍需经过数据治理与人工审核后才可用于训练。

## 7. 主要接口与安全控制

计划中的 API 包括：

| 接口 | 用途 |
| --- | --- |
| `POST /api/v1/classifications` | 提交单条工单并进行主模型分类 |
| `POST /api/v1/batches` | 上传 CSV，创建异步批量任务 |
| `GET /api/v1/batches/{id}` | 查看批次状态和逐行错误 |
| `GET /api/v1/reviews` | 查询人工复核队列 |
| `POST /api/v1/reviews/{ticket_id}/decisions` | 追加人工复核决定 |
| `GET /api/v1/taxonomies/current` | 读取当前标签与路由定义 |
| `GET /api/v1/audit/{request_id}` | 在授权范围内查看事件链 |
| `GET /healthz`、`/readyz`、`/metrics` | 存活、就绪和监控检查 |

PoC 的最小安全控制为：JWT 认证和 `admin`、`reviewer`、`observer` 三角色授权；对邮箱、手机号、银行账号/IBAN、发票号和模拟供应商标识做规则脱敏；日志不记录正文或凭据；`.env`、令牌和 API key 不进入版本库；LLM 出域默认关闭；并按数据类型配置保留期和可审计清理机制。

需要注意：规则脱敏不能保证发现所有真实 PII。任何真实企业数据接入前，仍必须完成数据映射、隐私影响评估和更严格的访问控制设计。

## 8. 验收指标与质量门槛

验收将区分“PoC 方法和系统是否达标”与“真实业务是否产生收益”：

| 维度 | 规划门槛 |
| --- | --- |
| 模型效果 | Macro-F1 ≥ 0.80；Micro-F1 ≥ 0.85 |
| 高风险保护 | `SUPPLIER_MASTER_CHANGE` 召回率 ≥ 0.95；高风险或低置信样本 100% 进入人工复核 |
| 双语一致性 | 中英文 Macro-F1 差值 ≤ 0.08 |
| 响应性能 | 不调用 LLM 的单条预测 P95 ≤ 800 ms（约定硬件、500 次测试） |
| 系统可靠性 | 核心 API 验收压测错误率 < 1% |
| 工程质量 | 单元、契约、集成和核心 E2E 测试全部通过，且无高危秘密泄漏 |

由于训练数据主要为公开和模拟数据，上述门槛只能证明 PoC 流程、保护策略和工程质量达到预期，不能证明生产效果。真实试点应另行衡量建议采纳率、二次转派率、分流时长和 SLA 违约率。

## 9. 未决问题与实施前需确认事项

- **周期**：尚未确定具体日历时间，需要把 M0–M4 里程碑映射到实际周数。
- **LLM**：云端 LLM 提供商、预算上限和启用范围尚未决定；主链路不依赖该选择。
- **验收环境**：最终演示硬件、CPU/GPU、内存和并发参数未知，性能测试必须随结果一并记录。
- **真实数据与业务基线**：当前没有真实企业历史数据承诺；真实接入前需重新评估数据合规、脱敏有效性、标签边界和业务基线。
- **标签可用性**：首版标签可能存在重叠或一致性不足，应在训练前使用 50–100 条双语样例进行双人试标，根据冲突记录调整、合并或延后低一致性标签。

## 10. 结论

该项目的目标是构建一个边界清晰、可追溯、可演示的企业发票工单智能分流 PoC：自动化只提供标签和路由建议，关键风险始终由人工决策。后续阶段应先冻结契约和验收口径，再以可运行的端到端垂直切片验证方案，而不是将本规划误认为已完成的生产系统。
